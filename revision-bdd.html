L'objectif : éliminer la redondance

Une base mal conçue va répéter des informations dans plusieurs lignes ou plusieurs tables. C'est le terreau idéal pour les anomalies :

Anomalies de mise à jour
On change l'adresse d'un client à un endroit, mais pas aux autres — la base devient incohérente.
Anomalies d'insertion
On ne peut pas ajouter un département tant qu'on n'a pas un employé à y mettre, car la table mélange les deux concepts.
Anomalies de suppression
On supprime le dernier employé d'un département et… on perd aussi l'information du département.

La normalisation est le processus qui découpe progressivement les tables pour faire disparaître ces problèmes, en s'appuyant sur les dépendances fonctionnelles.

Dépendance fonctionnelle (DF)

Définition
Soit R(A₁, …, Aₙ) et X, Y ⊆ {A₁, …, Aₙ}. On dit que X → Y (X détermine Y) si, pour toute instance de R et pour tous tuples t₁, t₂ : t₁[X] = t₂[X] ⟹ t₁[Y] = t₂[Y].

Autrement dit : si deux lignes ont la même valeur pour X, alors elles ont forcément la même valeur pour Y.

Exemple — table Voitures

-- Soit la table : Voiture(NumProprio, Nom, Ville, NumVéhicule, Marque, Date)

NumProprio → Nom
NumProprio → Ville
NumVéhicule → Marque
NumProprio, NumVéhicule → Date

Une DF est une contrainte sémantique : elle ne se déduit pas en regardant les données, elle se déclare à partir des règles métier.

DF élémentaire

X → A est élémentaire ssi :

  • A est un attribut unique
  • A ∉ X
  • Il n'existe pas de X' ⊂ X tel que X' → A (X est minimal)

On peut se limiter aux DFs élémentaires pour raisonner — c'est la couverture minimale.

DF triviale
X → Y est triviale si Y ⊆ X. Exemple : A, B → B. On les ignore en pratique.

Exemple plus complet

Table Cours(NomProf, Ville, Département, NomEtudiant, Age, NomCours, Note) :

DF validesDF invalides
NomProf → VilleAge → NomEtudiant
NomEtudiant → AgeNomProf, NomEtudiant → Ville
NomCours → NomProf
NomEtudiant, NomCours → Note

Clé candidate

Définition
X ⊆ R est une clé candidate de R ssi :
  • X → A₁, A₂, …, Aₙ (X détermine tous les attributs)
  • ∀ Y ⊂ X, Y ↛ A₁, …, Aₙ (X est minimal)

Une relation peut avoir plusieurs clés candidates. On en choisit une comme clé primaire, les autres deviennent des clés alternatives.

Méthode pratique

  1. Identifie tous les attributs déterminés uniquement par d'autres attributs (les déterminés purs) — ils ne font partie d'aucune clé.
  2. Identifie les attributs qui n'apparaissent jamais à droite d'une DF — ils sont obligatoirement dans toute clé.
  3. Cherche la combinaison minimale qui détermine tout le reste.

Les formes normales

Une cascade : chaque forme normale suppose la précédente.

1ère Forme Normale (1FN)

Règle
Tous les attributs sont atomiques — non composés, mono-valués. 
-- Pas en 1FN :
PERSONNE (Nom, Prénoms)         -- "Prénoms" peut contenir plusieurs valeurs
PERSONNE (Nom, Prénom, Adresse) -- "Adresse" est composée

-- Mise en 1FN :
PERSONNE1 (Nom, Prénom1, Prénom2)
PERSONNE2 (Nom, Prénom, NumRue, Rue, CodePostal, Ville)

2ème Forme Normale (2FN)

Règle
Elle est en 1FN et tout attribut hors clé dépend de la totalité de la clé (pas d'une partie seulement). 
-- Non 2FN : R(A, B, C, D) avec clé (A, B) et A → C
-- C ne dépend que de A (une partie de la clé)

-- Décomposition :
R1(A, B, D)
R2(A, C)

La 2FN ne se pose que si la clé est composée. Si la clé est un seul attribut, on est automatiquement en 2FN.

3ème Forme Normale (3FN)

Règle
Elle est en 2FN et aucun attribut non-clé ne dépend d'un autre attribut non-clé (pas de dépendance transitive). 
-- Non 3FN : R(A, C, D) avec clé A, et C → D
-- D dépend de A via C (transitivement)

-- Décomposition :
R1(A, C)
R2(C, D)

Forme Normale Boyce-Codd (BCNF)

Règle
Pour toute DF non triviale X → A, X contient une clé candidate.

BCNF est plus stricte que 3FN. Elles diffèrent quand un attribut fait partie d'une clé candidate mais dépend d'un attribut non-clé.

Récapitulatif
1FN
Attributs atomiques.
2FN
1FN + pas de DF d'une partie de la clé vers un non-clé.
3FN
2FN + pas de DF entre non-clés.
BCNF
Toute DF non triviale part d'une super-clé.

Algorithme de décomposition vers la 3FN

  1. Calculer la couverture minimale des DFs.
  2. Pour chaque DF X → A₁, …, Aₖ, créer une relation (X, A₁, …, Aₖ).
  3. S'il n'existe aucune relation contenant une clé de la relation universelle, en ajouter une avec une clé candidate.
  4. Supprimer toute relation entièrement incluse dans une autre.
Propriété fondamentale
Toute relation admet au moins une décomposition en 3FN qui :
  • préserve une couverture minimale de DFs
  • est sans perte (on peut reconstruire l'originale par jointure)

Exemple complet

R(NumEmployé, NomEmployé, NumService, NomService, NumChef)

DFs :
  NumEmployé → NomEmployé, NumService
  NumService → NomService, NumChef

-- Décomposition en 3FN :
Employé(NumEmployé, NomEmployé, #NumService)
Service(NumService, NomService, NumChef)

Vues virtuelles

Définition
Une vue est une table virtuelle dont les instances n'existent pas physiquement. C'est une table logique qui pointe sur une (ou plusieurs) tables physiques. Chaque appel à une vue exécute en réalité un SELECT.

Pourquoi des vues ?

Optimisation
Donner un nom à une requête longue qu'on utilise souvent.
Simplification
Réduire des tables complexes à des vues plus simples pour les utilisateurs métier.
Sécurité
Masquer certaines colonnes ou lignes aux utilisateurs.

Syntaxe — CREATE VIEW

CREATE [OR REPLACE] [TEMP] VIEW <nom_vue>
  [(nom_colonne [,…])] AS requête
  [WITH [CASCADED | LOCAL] CHECK OPTION]
TEMP
La vue est supprimée à la fin de la session.
CHECK OPTION
Les INSERT / UPDATE via la vue doivent respecter sa condition.
LOCAL
Vérification uniquement sur cette vue.
CASCADED
Vérification sur la vue et toutes ses vues-filles.

Exemple — vue avec jointure

CREATE VIEW tous AS
SELECT e.nom AS Employe, d.nom AS departement
FROM Employes e, Departement d
WHERE e.departement = d.id;

-- Utilisation : exactement comme une table
SELECT * FROM tous;

Exemple — vue dérivée d'une autre vue

CREATE VIEW les_dupont AS
SELECT * FROM tous
WHERE Employe = 'Dupont';

Suppression et renommage

DROP VIEW <nom_vue> [CASCADE | RESTRICT];
-- CASCADE : supprime aussi les objets qui en dépendent
-- RESTRICT : refuse si une dépendance existe (défaut)

RENAME <ancien> TO <nouveau>;

Vues matérialisées

Contrairement à une vue virtuelle, une vue matérialisée est stockée physiquement sur disque. On la crée avec CREATE MATERIALIZED VIEW.

Avantages
  • Temps de réponse améliorés (les requêtes en lecture sont instantanées)
  • Consommation réduite : le SGBD n'a pas à réexécuter la requête
  • Idéal pour les rapports d'analyse périodiques
Inconvénients
  • Espace de stockage supplémentaire
  • Données potentiellement obsolètes
  • Nécessite un rafraîchissement périodique (REFRESH MATERIALIZED VIEW)

À choisir quand la lecture est fréquente et la fraîcheur n'est pas critique.

Indexes

Sans index, le SGBD fait un full table scan : il parcourt toutes les lignes pour trouver celles qui correspondent à la clause WHERE. Avec un index, il navigue dans un arbre et atteint la donnée en O(log n).

Le B-Tree (Balanced Tree)

Les indexes sont stockés sous forme d'arbre équilibré. Chaque nœud contient des valeurs triées qui pointent vers les pages de données, ou vers d'autres nœuds plus profonds.

       [ 1 | 11 ]
        /        \
   [1|5|9]       [11|17]
   /  |  \        |   \
 1-4 5-8 9-10  11-15  17-21

Syntaxe MySQL

CREATE INDEX <nom_index> ON <nom_table> (col1, col2, ...);

-- Exemple
CREATE INDEX idx_person_genre ON person (genre);

-- Suppression
DROP INDEX idx_person_genre ON person;
Quand indexer ?
Sur les colonnes utilisées dans WHERE, JOIN ... ON, et ORDER BY — surtout si la table est grosse et que la cardinalité de la colonne est élevée.
Le coût des indexes
  • Espace disque supplémentaire
  • Ralentit les INSERT, UPDATE, DELETE (il faut mettre à jour l'arbre)
  • Inutile sur une colonne à faible cardinalité (genre M/F/Other sur une table tiny)

Droits d'accès

Une base sérieuse ne donne pas tous les pouvoirs à tous les utilisateurs. Le DBA (Database Administrator) accorde et révoque des droits avec GRANT et REVOKE.

Le super-utilisateur

Niveau DBA. C'est en général celui qui a créé la base. Il a deux droits exclusifs : créer des utilisateurs et créer des bases de données.

GRANT — accorder un droit

GRANT {SELECT | INSERT | UPDATE | DELETE | ALL PRIVILEGES}
  ON [TABLE] ma_table [,…]
  TO {user | GROUP name | PUBLIC} [,…]
  [WITH GRANT OPTION];
-- Tout le monde peut lire Client
GRANT SELECT ON Client TO PUBLIC;

-- Alice peut insérer dans Client
GRANT INSERT ON TABLE Client TO Alice;

-- Bob peut modifier/supprimer ET peut transmettre ces droits
GRANT UPDATE, DELETE ON TABLE Client
  TO Bob WITH GRANT OPTION;

-- Droits fins sur certaines colonnes seulement
GRANT INSERT, UPDATE (nom, adresse) ON Client TO Alice;
Astuce — pas de SELECT par colonne
On ne peut pas restreindre le SELECT à certaines colonnes. La solution : créer une vue qui n'expose que ces colonnes, puis GRANT SELECT sur la vue.

REVOKE — supprimer un droit

REVOKE [GRANT OPTION FOR] {SELECT | INSERT | …}
  ON [TABLE] ma_table [,…]
  FROM {user | GROUP name | PUBLIC} [,…]
  [CASCADE | RESTRICT];
-- Retire au groupe PUBLIC le droit d'insertion
REVOKE INSERT ON films FROM PUBLIC;

-- Retire TOUS les droits de Bob sur la vue Genres
REVOKE ALL PRIVILEGES ON genres FROM Bob;
Limite du REVOKE
Le pouvoir de révocation est limité aux droits qu'on a soi-même accordés. Paul, qui avait donné un INSERT à Alice, ne peut révoquer que ce droit, pas un autre.

Rôles

Un rôle est un ensemble de droits qu'on attribue à plusieurs utilisateurs. Plus maintenable que de gérer chaque droit individuellement.

CREATE ROLE vendeur;
GRANT SELECT, INSERT ON commandes TO vendeur;
GRANT vendeur TO Alice, Bob;

-- Retire le rôle à Alice
REVOKE vendeur FROM Alice;

Qu'est-ce qu'une transaction ?

Définition
Une transaction est une unité logique de travail regroupant plusieurs opérations qui doivent toutes réussir, ou toutes échouer. Soit on valide l'ensemble (COMMIT), soit on annule tout (ROLLBACK).

Exemple classique : transfert bancaire

START TRANSACTION;
UPDATE comptes SET solde = solde - 100 WHERE id = 1;
UPDATE comptes SET solde = solde + 100 WHERE id = 2;
COMMIT;
-- ou ROLLBACK si quelque chose tourne mal

Si la 2ᵉ instruction échoue, on ne veut surtout pas que la 1ʳᵉ soit validée : on perdrait 100€.

Autocommit

autocommit = ON (défaut)
Chaque instruction est sa propre transaction, validée immédiatement.
autocommit = OFF
Les instructions s'accumulent jusqu'à un COMMIT ou ROLLBACK explicite.
START TRANSACTION
Démarre explicitement une transaction même en mode autocommit ON.

Les 4 propriétés ACID

Tout SGBD relationnel digne de ce nom garantit ces 4 propriétés pour ses transactions.

A
Atomicité
Tout ou rien. Si une opération échoue, toutes les autres sont annulées. Garantie par COMMIT / ROLLBACK.
C
Cohérence
La base passe d'un état cohérent à un autre. Les contraintes (clés, CHECK, FK) doivent rester valides après chaque transaction.
I
Isolation
Deux transactions concurrentes ne doivent pas se voir mutuellement avant le COMMIT. Garantie par des verrous.
D
Durabilité
Une fois committée, une transaction est gravée — même en cas de panne. Garantie par les LOGS (write-ahead logging).

Anomalies de concurrence

Sans isolation, voici les 4 désastres classiques qui arrivent quand plusieurs transactions s'exécutent en parallèle.

Dirty Read (lecture sale)
T1 lit une donnée que T2 a modifiée mais pas encore committée. Si T2 fait ROLLBACK, T1 a lu une donnée qui n'a jamais existé.
Lost Update (mise à jour perdue)
T1 et T2 lisent la même valeur, la modifient chacune, puis écrivent. La 2ᵉ écriture écrase la 1ʳᵉ : un des deux updates est perdu.
Non-repeatable Read (lecture non reproductible)
T1 lit une ligne, T2 la modifie et commit, T1 la relit et trouve une valeur différente. Mauvais si T1 fait des calculs cohérents.
Phantom Read (lecture fantôme)
T1 fait SELECT avec un WHERE. T2 insère une ligne qui correspond au WHERE et commit. T1 refait le SELECT : une nouvelle ligne « fantôme » apparaît.

Sérialisabilité & équivalence de conflits

Exécution sérielle
Les transactions s'exécutent l'une après l'autre, sans entrelacement. Toujours correcte, mais lente.
Exécution concurrente sérialisable
Les transactions s'entrelacent, mais le résultat final est identique à une exécution sérielle. C'est le Saint Graal.

Équivalence de conflits

Deux opérations sont en conflit si :

  • Elles appartiennent à deux transactions différentes
  • Elles accèdent au même élément
  • Au moins une des deux est une écriture

Donc les paires en conflit sont : R/W, W/R, W/W. Pas R/R.

Deux exécutions sont équivalentes par conflit si on peut transformer l'une en l'autre en permutant des opérations non conflictuelles. Si une exécution est équivalente à une exécution sérielle → elle est sérialisable.

Verrous (locks)

Mécanisme principal pour garantir l'isolation.

Verrou partagé S (Shared)
Posé pour lire. Plusieurs transactions peuvent avoir un verrou S simultanément sur la même donnée.
Verrou exclusif X (eXclusive)
Posé pour écrire. Aucune autre transaction ne peut avoir de verrou (S ou X) en même temps.

Strict 2-Phase Locking (S2PL)

Protocole standard : tous les verrous (S et X) sont relâchés uniquement à la fin de la transaction (au COMMIT ou ROLLBACK). Garantit la sérialisabilité.

Deadlock (interblocage)

Définition
T1 attend un verrou détenu par T2, et T2 attend un verrou détenu par T1. Aucune ne peut avancer.
Prévention
Ordre fixe d'acquisition des verrous (toutes les transactions verrouillent les tables dans le même ordre).
Détection
Le SGBD construit un graphe d'attente. Si un cycle apparaît → il tue une des transactions (la « victime »).

Programmes stockés

Définition
Un programme stocké est du code compilé et exécuté côté serveur. Il existe deux formes principales : les procédures (qu'on appelle explicitement avec CALL) et les triggers (déclenchés automatiquement).

Pourquoi ?

Performance
Précompilé une fois, exécuté plein de fois — pas d'aller-retour réseau.
Sécurité
L'utilisateur appelle la procédure sans avoir besoin de droits directs sur les tables.
Réutilisation
Une logique métier centralisée, partagée entre toutes les applis qui parlent à la base.
Intégrité
Les triggers garantissent que certaines règles métier sont toujours appliquées.

Procédures stockées (MySQL)

Syntaxe

DELIMITER //
CREATE PROCEDURE nom_proc(IN p1 INT, OUT p2 VARCHAR(50))
BEGIN
  -- corps de la procédure
  SELECT nom INTO p2 FROM employes WHERE id = p1;
END//
DELIMITER ;

Le DELIMITER // est nécessaire car le corps de la procédure contient des ;. Sans ça, MySQL exécuterait chaque instruction interne séparément.

Paramètres

IN
Paramètre d'entrée (défaut). Lu par la procédure.
OUT
Paramètre de sortie. Écrit par la procédure, récupéré par l'appelant.
INOUT
Les deux : on passe une valeur, la procédure peut la modifier.

Appel

CALL nom_proc(42, @resultat);
SELECT @resultat;

Suppression

DROP PROCEDURE [IF EXISTS] nom_proc;

Fonctions stockées

Une fonction est comme une procédure, mais elle retourne une valeur et s'utilise dans des expressions SQL (SELECT, WHERE…).

DELIMITER //
CREATE FUNCTION bonus(salaire DECIMAL(10,2))
RETURNS DECIMAL(10,2)
DETERMINISTIC
BEGIN
  RETURN salaire * 0.10;
END//
DELIMITER ;

-- Utilisation
SELECT nom, salaire, bonus(salaire) FROM employes;
DETERMINISTIC
Pour les mêmes entrées, retourne toujours la même sortie (sans effet de bord).
NOT DETERMINISTIC
La sortie peut varier (ex : utilise NOW(), RAND()).

Procédure vs Fonction

Procédure
Appelée avec CALL. Peut ne rien retourner ou utiliser OUT.
Fonction
Appelée dans une expression. Retourne TOUJOURS une valeur via RETURN.

Variables

Variables utilisateur — @nom
Préfixées par @. Persistent toute la durée de la session. Pas besoin de DECLARE. 
SET @total = 0;
SELECT SUM(montant) INTO @total FROM ventes;
SELECT @total;
Variables locales — DECLARE
Déclarées dans un bloc BEGIN…END. N'existent que dans ce bloc. 
BEGIN
  DECLARE compteur INT DEFAULT 0;
  SET compteur = compteur + 1;
END
Variables système — @@nom
Préfixées par @@. Configuration du serveur. Ex : @@version, @@autocommit.

Triggers (déclencheurs)

Définition
Un trigger est un programme stocké qui s'exécute automatiquement avant ou après un INSERT, UPDATE ou DELETE sur une table donnée.

Syntaxe (MySQL)

CREATE TRIGGER nom_trigger
{BEFORE | AFTER} {INSERT | UPDATE | DELETE}
ON nom_table
FOR EACH ROW
BEGIN
  -- corps du trigger
END;

Accéder aux valeurs

NEW.col
Disponible pour INSERT et UPDATE. La nouvelle valeur.
OLD.col
Disponible pour UPDATE et DELETE. L'ancienne valeur.

Exemple — borner un montant entre 0 et 100

DELIMITER //
CREATE TRIGGER borner_montant
BEFORE INSERT ON ventes
FOR EACH ROW
BEGIN
  IF NEW.montant < 0 THEN SET NEW.montant = 0;
  ELSEIF NEW.montant > 100 THEN SET NEW.montant = 100;
  END IF;
END//
DELIMITER ;

Cas d'usage typiques

  • Audit : journaliser chaque modification d'une table sensible
  • Validation : refuser ou corriger les valeurs invalides
  • Cascade métier : mettre à jour des compteurs, des stocks, des soldes…
  • Historique : copier l'ancienne ligne dans une table d'archive avant UPDATE/DELETE
